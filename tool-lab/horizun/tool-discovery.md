# Horizun Revit MCP — tool discovery (P02-T06)

Discovered 2026-09-15 from the **installed server itself**, not from a client.
Revit was closed for the whole discovery, so no tool was callable; the catalog is
still truthful, because `tools/list` and the contract resource are answered by
the MCP server process, not by the Revit add-in.

## Why not `/mcp` and a Codex restart

Plan 02 Task 6 assumed the catalog could only be read after restarting Codex and
running `/mcp`. That is a client-side view of the same data, and a restart is an
expensive way to obtain it. `tool-lab/horizun/mcp_probe.py` speaks the same
stdio JSON-RPC 2.0 transport the client uses — initialize, `tools/list`,
`resources/list`, `resources/read` — directly to the installed
`horizun-mcp.exe`. The result is the server's own answer, reproducible without
touching the Codex configuration.

```powershell
& "./.venv/Scripts/python.exe" tool-lab/horizun/mcp_probe.py --list --resources --json tool-lab/horizun/probe.json
& "./.venv/Scripts/python.exe" tool-lab/horizun/mcp_probe.py --call horizun_health --timeout 90
```

## The finding that changed the plan

The client tool listing returns **70** tools. The resource
`horizun://contract/tools`, published by the same server, declares **80**
(`protocol_version: 2`, `contract_hash: 8b9600f5274d7dffb6e5bd5f`). Every one
of the 70 is in the contract; **10 exist only in the contract**:

```text
horizun_save_document      horizun_open_document     horizun_document_session
horizun_export             horizun_execute_python    horizun_capture_view
horizun_create_family      horizun_relinquish_all    horizun_excel_write_rows
horizun_power_bi_push
```

Those ten are exactly the tools Plan 02 Task 6 needed and could not name: save,
PDF/IFC/DWG/image export, and custom Python. A discovery that stopped at
`tools/list` would have recorded five capabilities as missing that are in fact
installed. The contract resource is therefore the authority, and
`state/providers/horizun-toolmap.yaml` records both counts so nobody has to
rediscover the difference.

The server's own `horizun://build/identity` explains the relationship: every
published tool is "host-resident, or a plugin command the loaded add-in
registers". The contract lists the full set the add-in can register; the client
listing reflects what the running bridge has published so far.

## The toposolid gap

The site capability has **no creation path** in this contract. Searching the whole
contract for `toposolid` and `topograph` matches three tools, and none creates a
surface.

- `horizun_embed_floors_in_toposolid` edits an existing toposolid.
- `horizun_grade_toposolid_around_floors` edits an existing toposolid.
- `horizun_execute_plan` only lists them among its 21 action tools.

`horizun_create_elements` accepts 26 element kinds and **toposolid is not one of
them**. The exact 26 kinds are recorded in the toolmap under
`capabilities.site_toposolid.contract_scan.creation_tool_element_kinds`, so the
absence is auditable rather than asserted.

Two verified alternatives exist, both recorded in the toolmap:

1. Place the toposolid once by hand in Revit, then use
   `horizun_grade_toposolid_around_floors` and `horizun_embed_floors_in_toposolid`
   to work against it.
2. Request arbitrary Python with `horizun_request_python_access` and call the
   Revit API surface builder through `horizun_execute_python`.

**Route 2 is now proven on this machine** (P02-T12, 2026-09-15). `Toposolid.Create`
built the synthetic `[0,0,0.0] [20,0,0.5] [20,20,1.0] [0,20,0.5]` m plane from the
plan on a fresh baseline copy, first in a rehearsal that was rolled back and then in a
committed transaction (element 328673, 9/9 postconditions), and the result was re-read
by typed `horizun_query_model` queries with extents 0–20 m and survived a
save/close/reopen cycle. Route 1 (hand-placed) is still unexercised. The full
transcript is `tool-lab/horizun/results/t12-toposolid.json`.

What that does **not** change: there is still no typed creation path in the contract,
and the project's own site data still records topography as `MISSING` with a planar
placeholder. So blocker `SITE_TOPOGRAPHY` stays open — the proof covers the
*mechanism* (arbitrary Python can build and persist a surface), not the *data*, and no
production Toposolid support is claimed.

## Reproducing and regenerating

```powershell
# refresh the catalog and the contract capture
& "./.venv/Scripts/python.exe" tool-lab/horizun/mcp_probe.py --list --resources --json tool-lab/horizun/probe.json

# rebuild the toolmap from the verified artifacts, or verify it is current
& "./.venv/Scripts/python.exe" tool-lab/horizun/generate_toolmap.py
& "./.venv/Scripts/python.exe" tool-lab/horizun/generate_toolmap.py --check

# the enforcement tests
& "./.venv/Scripts/python.exe" -m pytest tests/providers -q -p no:cacheprovider
```

`generate_toolmap.py` refuses to write a capability whose tool name is absent from
the union of the catalog and the contract, whose element kind is not a variant of
`horizun_create_elements`, whose operation is not in the `horizun_manage_views`
enum, or whose export format is not in the `horizun_export` enum. It caught one
such name during development (`horizun_list_warnings`), which is the point: a
guessed name cannot reach the committed file.

## What this discovery does not establish

- **Superseded for most rows.** This list was written at discovery time, before any
  live call. Tasks P02-T05 and P02-T07..T12 have since invoked the bridge against a
  live Revit 2027 and are recorded as `PASS` with their own transcripts under
  `tool-lab/horizun/results/`. What follows is what is *still* unestablished.
- Nothing here is a claim about **production** behaviour: every proof is on
  synthetic geometry in throwaway lab copies, not on the project model.
- The hand-placed toposolid route (route 1 above) has never been exercised; only the
  Python route has.
- `horizun_execute_python` results are always `self_reported_verified` from the
  bridge's point of view, so Python work is only ever confirmed by a separate typed
  query — never by the script's own report.
- The room-tag capability is `DEGRADED` in this template: tagging an `OST_Rooms`
  reference fails in Revit for every room tag type present, in both `tag_mode`
  values. That was proven by a rolled-back rehearsal, not assumed (P02-T11).
- `horizun_export` with `format: image` is `DEGRADED`: ExportImage treats the
  supplied path as a stem and appends the view type and name, so the reported path
  is not the written path; success was therefore not claimed (P02-T11).
- The 10 contract-only tools were not listed by the client during discovery. Their
  first real calls are now proven for the document, save, export and Python ones;
  the remainder still rest on the contract schema alone.
